# Device lab direction — product clarification, 2026-09-17

The user wants an immersive, brand-neutral Interactive Leaks experience, including custom builds and comparable simulated workloads. This clarification extends the long-term interface direction. It does not authorize fabricated benchmark results or replace the accepted model validation gates.

## Experience

An interactive device canvas sits beside a component inspector and readable results. Users can begin from a sourced rumored device or a custom configuration. Component choices update the visual assembly; accessible form controls and result tables provide the same functionality without animation. Respect reduced-motion preferences and limit graphics work on mobile.

Use clearly distinct input types: reported claim with evidence, measured calibration value, user assumption and unknown. User builds must not appear as actual product leaks. A geometric device illustration is not proof of industrial design. Add photorealistic/3D assets only where performance, licensing and fidelity justify them.

## Engine contract

Keep a pure, versioned TypeScript calculation module independent of brand, renderer and database. A supported model declares units, input bounds, required component characteristics, workload definitions and calibration coverage. Validate component compatibility as well as scalar ranges. Unknown or out-of-range configurations return an explanation instead of invented coefficients.

Client-side previews may use the identical deterministic module. The server validates the complete input and recomputes before persisting a verified run. Clients cannot submit authoritative output or achievement scores. Bound execution and request sizes to the free hosting budget; reassess execution placement with measurements before adding expensive models.

Persist an immutable input snapshot, evidence revision references, user overrides, model/scenario versions, outputs, uncertainty method and timestamp. New rumor information does not alter old runs. Only compare compatible model/workload versions; retain reproducibility after model upgrades.

## Benchmark distinction

Real benchmark software executes workloads on physical devices. PhoneFuturist initially simulates scenarios from assumptions and calibration data. Call the outputs simulated estimates, not measured Geekbench scores. An eventual PhoneFuturist score needs its own disclosed workload, reference configuration, validation evidence and version. Arbitrary cross-brand scores or universal performance extrapolation are out of scope.

## Delivery order

Publication and Studio are the immediate product priority. Preserve the accepted milestone roadmap. Milestone 5 begins with the calibrated battery-energy/endurance engine, supported workload comparisons and custom inputs inside validated limits. CPU/GPU, charging and thermal engines follow only after their own evidence and validation. A named methodology owner must approve public release; no LLM supplies numerical results.
