# Virtual Device generation — Phase 2

Server entry point: `createVirtualDeviceInferenceService` in `src/lib/simulation/virtual-device-inference.ts`.
No HTTP route, database, UI, runner, subscription or live provider invocation is added by this phase.

## Generation and trust boundaries

1. Strictly parse a configuration. Its assertions and evidence IDs are unverified user context.
2. Assemble all five categories from an application-owned, versioned catalog. Clone and validate records; select the target and explicit related devices. Never take the catalog, relationship graph, policy, clock, IDs or previous revision from HTTP request JSON.
3. Build fixed direct-evidence/unknown parameter slots and approved prediction slots. Conflicting direct records stop generation. Source metadata is copied from the server catalog, never from the proposal.
4. Send one structured whole-device prompt, snapshot, policy decisions and strict output schema through the shared Cloudflare Responses transport.
5. Strictly parse the object. No JSON repair, markdown stripping, numeric coercion, extra fields or provider-assigned model/snapshot/revision identity.
6. Require exact slot coverage. Fixed parameters cannot change. Only predicted or unknown output is allowed for approved prediction slots. Predictions preserve the complete approved envelope and exact conditions, evidence references and low confidence cap.
7. Optionally derive pack Wh from explicit compatible pack mAh and nominal V. This single allowlisted arithmetic derivation preserves the full interval and predicted lineage. No voltage default, no endurance computation, no arbitrary provider derivation methods.
8. Assign server identity, timestamps and revision; run the unchanged Phase 1 validator. Run additional cross-domain necessary engineering checks. Deep-freeze the accepted model **and its configuration/evidence/policy/relationship receipt**.

`accepted` means a validated model, not simulation readiness. A model can contain only unknowns. Consumers must inspect required parameter coverage before running a test. No persistent immutability or concurrent append guarantee is claimed: Phase 3/storage must provide atomic revision handling when persistence is introduced. Keep the complete accepted receipt, not just the model.

## Analogy policy v1

Policies are reviewed server configuration, never generated by AI. Each policy specifies target, parameter, operating conditions, source IDs, an explicit engineering uncertainty envelope and rationale. At least two distinct reference devices with non-predicted evidence for the same quantity and exact conditions are required. Each must have a curated predecessor, comparable-SoC or comparable-device relationship. Same-brand context is included but is insufficient alone. Missing, duplicate, ambiguous-revision or mismatched references fail closed. User assertions cannot create a relationship or authorize evidence.

This conservative sufficiency rule and low confidence ceiling are acceptance policy, **not empirical accuracy or calibrated coverage probabilities**. The approved envelope is retained in full rather than allowing an LLM to invent precision. The provider contributes synthesis, assumptions, dependency links and explicit abstention. A reviewed future policy version may support narrower empirically justified envelopes; do not weaken ADR-013 to accommodate output.

The reusable catalog supports Battery, CPU, GPU, Thermal and Charging records. No production CPU/GPU/thermal/charging dataset is invented. The battery adapter reuses existing reference watts as **derived** evidence, excludes held-out validation observations, and grants no automatic analogy approvals. Existing battery records have a provenance discrepancy: some populated energy/voltage fields still carry unresolved-evidence notes. New policies must review the underlying pack-energy sources first. Legacy calculations remain unchanged.

## Sanity checks and limitations

The unchanged contract validator enforces bounds, units, lineage, dependencies, conditions, revision semantics and charging peak limits. Additional checks reject disjoint pack energy/capacity/voltage ranges, component or combined CPU/GPU draw exceeding whole-device draw, contradictory same-protocol CPU scores, impossible charging input/efficiency/accepted-power combinations and steady-state thermal power exceeding its throttle envelope. Cross-domain comparisons require compatible conditions; charging peak/efficiency may omit the instantaneous state of charge.

These are necessary checks, not full models. They do not validate benchmark calibration, FPS mappings, charging curves or transient thermal behavior. Those belong to subsequent runners. Predicted engineering values remain uncertain. Unverified user assertions do not replace source records; unsupported assertions may leave the corresponding model field unknown.

## Failures and compatibility

Typed rejection stages: configuration, evidence, provider, parse, provenance, engineering. Nothing is accepted on failure; no repair, fallback voltage, automatic retries or fabricated model. Provider errors returned by the service are generic, excluding raw upstream bodies or credentials. Transport timeout/abort cleanup and legacy request/response/error behavior are preserved. Legacy battery API, contracts, calibration and Advanced Mode are untouched.

## Phase 3 prerequisites

- Curate actual per-domain sources, device relationships and reviewed analogy envelopes; resolve legacy battery provenance before approving new analogies.
- Integrate authenticated/rate-limited server composition and deployment configuration without exposing catalog authority or credentials to clients.
- Add category-specific readiness and reusable test requests/runners, reusing the existing endurance engine rather than creating another.
- Validate benchmark/thermal/charging semantics against real technical data; add empirical calibration and abstention criteria.
- If approved later, persist immutable model/evidence/policy receipts with atomic revision updates, then connect UI and result disclosures.
